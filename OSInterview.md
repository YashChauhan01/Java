## Category 1: Process Management & CPU Scheduling

### 1. Process vs Thread — memory space, context-switching overhead, resource sharing
A **Process** has its own **isolated address space** (separate heap, code, data segments) — the OS allocates it a fully independent memory region, so two processes cannot accidentally read/write each other's memory. A **Thread** is a lightweight execution unit *within* a process; all threads of the same process **share the same heap, code segment, and open file descriptors**, but each thread gets its **own stack, program counter, and register set**. Consequently:
- **Context-switching between processes** is expensive — the OS must switch the entire memory address space (flush/reload MMU page tables, invalidate CPU caches/TLB).
- **Context-switching between threads of the same process** is cheap — the address space stays the same; only the stack pointer, registers, and program counter change.
- **Resource sharing**: threads share memory/resources by default (fast communication, but requires synchronization to avoid races); processes are isolated by default (safer, but inter-process communication requires explicit mechanisms like pipes, shared memory, or sockets).

### 2. Process Control Block (PCB) structure and process lifecycle states
The **PCB** is a kernel data structure the OS maintains per process, storing everything needed to manage and later resume it: **Process ID (PID)**, **process state**, **CPU register values** (saved on context switch), **program counter**, **CPU scheduling info** (priority, scheduling queue pointers), **memory management info** (page tables, base/limit registers), **I/O status info** (open files, allocated devices), and **accounting info** (CPU time used, time limits). A process cycles through these states:
- **New**: being created.
- **Ready**: loaded into memory, waiting for the CPU scheduler to give it CPU time.
- **Running**: actively executing on a CPU core.
- **Waiting/Blocked**: paused, waiting on an I/O operation or event to complete.
- **Terminated**: finished execution (or killed); PCB is deallocated after the parent collects exit status.

### 3. What happens during a Context Switch, and why it's expensive for low-latency banking systems
A context switch occurs when the CPU stops executing one process/thread and starts executing another. The OS: (1) saves the current process's execution state (register values, program counter, stack pointer) into its **PCB**; (2) selects the next process/thread to run via the scheduler; (3) loads that process's saved state from its PCB back into the CPU registers; (4) if switching between **processes** (not threads of the same process), also switches the **memory address space** — updating the MMU/page table base register, which invalidates the **TLB** and CPU caches, since the new process's virtual-to-physical mappings are entirely different. This is expensive because: it consumes CPU cycles doing pure bookkeeping (zero useful work done); it causes **cache and TLB misses** immediately after the switch, since the new process's working set isn't cached yet, forcing slower memory accesses until the cache "warms up" again. In a low-latency trading system, even microseconds of pure scheduling overhead per switch, multiplied across thousands of switches per second, translates directly into missed trade execution windows — which is why such systems often use CPU pinning/affinity and minimize unnecessary thread proliferation to reduce switch frequency.

### 4. Preemptive vs Non-Preemptive scheduling
- **Preemptive**: the OS can **forcibly suspend** a running process (e.g., because a higher-priority process becomes ready, or its time quantum expires) and give the CPU to another process, without the current process's cooperation. Examples: **Round Robin**, **Preemptive Priority Scheduling**, **Multi-Level Feedback Queue**.
- **Non-Preemptive**: once a process starts running, it **keeps the CPU until it voluntarily yields** (completes, or blocks on I/O) — the OS cannot interrupt it mid-execution to run something else. Examples: **First-Come-First-Served (FCFS)**, **Non-preemptive SJF (Shortest Job First)**.
Preemptive scheduling gives better responsiveness and fairness (critical for interactive/real-time systems like trading platforms) but adds context-switch overhead and the complexity of protecting shared data from being modified mid-operation when preempted; non-preemptive is simpler and has zero mid-task interruption overhead, but a single long-running process can starve everything else.

### 5. Round Robin (RR) — mechanics and time quantum trade-offs
RR assigns each process a fixed **time quantum**; processes are held in a circular ready queue, and each gets to run for at most one quantum before being preempted and moved to the back of the queue, giving the next process its turn. This guarantees every process gets regular CPU access — no starvation, good responsiveness for interactive workloads.
- **Quantum too small**: the system spends a disproportionate amount of time on **context-switch overhead relative to actual useful work per turn** — throughput degrades because so much CPU time is consumed just switching, not computing.
- **Quantum too large**: RR effectively **degenerates into FCFS** — each process runs to completion (or close to it) before switching, losing the responsiveness/fairness benefits RR is meant to provide, and interactive/short tasks suffer poor response time waiting behind long ones.
The practical goal is a quantum large enough that context-switch overhead is a small fraction of the quantum, but small enough that no process waits too long for its turn — usually tuned empirically (commonly cited rule of thumb: 80% of CPU bursts should be shorter than the quantum).

### 6. Multi-Level Feedback Queue (MLFQ) — adapting to CPU-bound vs I/O-bound processes
MLFQ uses **multiple ready queues at different priority levels**, each typically with a different (usually increasing) time quantum, and **dynamically moves processes between queues** based on observed behavior — hence "feedback." A process that **uses its full time quantum** (behaving CPU-bound — it keeps wanting more CPU) gets **demoted** to a lower-priority queue with a longer quantum, since it's clearly compute-heavy and doesn't need frequent scheduling. A process that **voluntarily gives up the CPU before its quantum expires** (typically because it's waiting on I/O — behaving I/O-bound, e.g., a request handler waiting on a network/DB call) **stays at or is promoted to a higher-priority queue**, since I/O-bound processes need to be scheduled quickly and briefly whenever they become ready again, to keep I/O devices busy and the system responsive. This self-tuning behavior means MLFQ doesn't need the process to declare its nature upfront — it infers CPU-bound vs. I/O-bound purely from runtime behavior and adjusts priority accordingly.

### 7. Starvation and Aging
**Starvation (indefinite blocking)** occurs when a process is perpetually denied CPU time because the scheduler keeps favoring other processes ahead of it — e.g., in **SJF**, a long process can wait forever if a continuous stream of shorter jobs keeps arriving and always gets prioritized; in **Priority Scheduling**, a low-priority process can starve if higher-priority processes keep arriving. **Aging** mitigates this by **gradually increasing a waiting process's priority the longer it waits** — so even a low-priority or long-burst process eventually accumulates enough "aged" priority to guarantee it gets scheduled, bounding the maximum wait time and preventing indefinite starvation, without requiring the scheduler to abandon its original prioritization scheme for freshly-arrived processes.

### 8. User-Level Threads (ULT) vs Kernel-Level Threads (KLT); mapping models
- **User-Level Threads**: managed entirely by a **user-space thread library**, with the kernel completely unaware individual threads exist — it only sees one process. Extremely fast to create/switch (no kernel involvement, no system call/mode-switch overhead) but has a critical downside: if **one** ULT makes a **blocking system call**, the **entire process blocks** (since the kernel only knows about the process, not its internal threads), stalling all other ULTs within it.
- **Kernel-Level Threads**: created, scheduled, and managed **directly by the OS kernel** — the kernel is aware of and schedules each thread individually. A blocking call by one KLT doesn't block sibling threads, and KLTs can truly run in parallel across multiple CPU cores. Costs more overhead per creation/switch since it involves the kernel.
Mapping models:
- **Many-to-One**: many ULTs map to a single KLT — fast thread management, but no true parallelism and the blocking-call problem above.
- **One-to-One**: each ULT maps directly to its own KLT — true parallelism, no blocking-call problem, but thread creation/context-switching is more expensive (Java and modern Linux/Windows threads use this model).
- **Many-to-Many**: many ULTs multiplexed across a smaller or equal number of KLTs — the OS/library balances threads across available kernel threads, aiming to get parallelism benefits while keeping creation overhead lower than strict one-to-one.

### 9. Thread Pools — why per-request thread spawning is an anti-pattern
A **Thread Pool** pre-creates and maintains a fixed (or bounded, dynamically-sized) set of worker threads that **sit idle waiting for tasks**, pulling from a shared task queue as requests arrive — threads are **reused** across many requests rather than created fresh each time. Dynamically spawning a brand-new OS thread for every incoming transaction request is an anti-pattern in high-throughput servers because: (1) **thread creation itself has real, non-trivial overhead** — allocating a new stack, registering with the kernel scheduler — that adds latency to every single request; (2) under a traffic spike, **unbounded thread creation can exhaust system resources** (memory for thread stacks, kernel scheduling overhead across thousands of live threads, excessive context-switching thrashing the CPU) potentially crashing the entire service; (3) it provides **no natural back-pressure/throttling mechanism** — a thread pool's bounded size naturally queues excess work instead of letting the system get overwhelmed, giving predictable, controlled degradation under load rather than catastrophic resource exhaustion. This directly parallels why you use connection pooling for databases (from your DBMS prep) — reusing an expensive-to-create resource instead of paying its setup cost on every request.

### 10. Daemon Process vs standard background process
A **Daemon Process** is a special kind of background process that runs **continuously, detached from any controlling terminal**, typically starting at system boot and running for the system's entire lifetime to provide an ongoing service (e.g., `sshd`, `cron`, a logging service, a database server process). Key distinguishing traits: it has **no controlling terminal/user session** attached (so it survives a user logging out), it's typically started by the **init system** rather than an interactive shell, and it usually runs with **elevated or specific service-account privileges** rather than a regular user's session privileges. A regular **background process** is just any process a user launched and sent to the background (e.g., `command &` in a shell) — it's still tied to that user's session in some ways (may be terminated when the session ends, depending on shell/`nohup` settings) and isn't necessarily designed to run indefinitely as a system service.

## Category 2: Process Synchronization & Concurrency Control

### 11. Critical Section Problem — the three mandatory requirements
The **Critical Section** is the segment of code where a process accesses shared resources (e.g., a shared account balance) that must not be concurrently modified by another process. A valid solution to coordinating access must guarantee:
1. **Mutual Exclusion**: at most **one** process may execute in its critical section at any given time — no two processes can simultaneously modify the shared resource.
2. **Progress**: if no process is currently in its critical section and some processes wish to enter, the decision of **which one enters next cannot be postponed indefinitely** — the selection must happen in finite time, and processes not in their critical/remainder section can't block this decision.
3. **Bounded Waiting**: there must be a **finite bound** on the number of times other processes are allowed to enter their critical section after a process has requested entry and before that request is granted — preventing any single process from being made to wait forever (this is essentially the formal, structural guarantee against starvation).

### 12. Mutex vs Semaphore
- **Mutex (Mutual Exclusion Lock)**: a **binary, ownership-based** lock — only the thread that **acquired** it can **release** it, and it strictly allows only one thread to hold it at a time. Conceptually it's about **protecting a critical section** ("only I am allowed in here right now").
- **Semaphore**: an **integer counter**-based synchronization primitive, supporting `wait()`/`acquire()` (decrement) and `signal()`/`release()` (increment) — a **binary semaphore** (count capped at 1) behaves similarly to a mutex in effect, but critically **has no ownership concept**: any thread can call `release()` on it, even one that never called `acquire()` — it's fundamentally a **signaling mechanism between threads**, not strictly an exclusive-access lock. A **counting semaphore** (count > 1) allows **up to N threads** to hold a permit simultaneously — used to limit concurrency on a resource pool (e.g., max 10 concurrent DB connections), which a mutex conceptually can't express since a mutex is inherently binary/exclusive.
The key conceptual distinction interviewers want: mutex = ownership + locking; semaphore = signaling + counting, and a semaphore can be used across threads/processes for coordination in ways a mutex's ownership model doesn't naturally support.

### 13. Spinlock — what it is, and when preferred over a blocking lock
A **Spinlock** is a lock where a thread trying to acquire it, if the lock is already held, **actively loops ("spins") in a tight busy-wait**, repeatedly checking if the lock has been released — rather than yielding the CPU and going to sleep (as a traditional blocking mutex would). This burns CPU cycles while waiting, which sounds wasteful, but it's **preferred over a blocking lock in scenarios where the expected wait time is very short** — specifically shorter than the cost of a full context switch (put thread to sleep, later wake it up and reschedule it). If the critical section guarded by the lock is tiny and typically held for only a few CPU instructions (very common **inside kernel code / low-level systems programming**, e.g., protecting a brief pointer update), spinning briefly is actually **faster** than paying the context-switch overhead of sleeping and being woken up. Spinlocks are generally **only appropriate on multi-core systems** (so the lock holder, running on a different core, can actually make progress and release it while the spinning thread wastes cycles on its own core) and are avoided for long critical sections or in single-core contexts, where spinning would just waste the only CPU available with zero chance of the lock being released concurrently.

### 14. Priority Inversion, and how Priority Inheritance Protocol fixes it
**Priority Inversion** happens when a **high-priority** thread is blocked waiting for a lock held by a **low-priority** thread, and one or more **medium-priority** threads (that don't need that lock) keep preempting the low-priority thread, preventing it from ever finishing and releasing the lock — effectively, the high-priority thread is stuck waiting behind medium-priority threads, inverting the intended priority order. This is a real, historically famous bug (it caused the Mars Pathfinder rover's watchdog resets in 1997). **Priority Inheritance Protocol** fixes it by **temporarily boosting the lock-holding low-priority thread's priority to match the highest-priority thread waiting on that same lock**, for as long as it holds the lock. This ensures medium-priority threads **can no longer preempt** the (temporarily boosted) lock holder, so it can run, finish its critical section, and release the lock promptly — after which its priority reverts to its original level, and the high-priority thread can then acquire the lock and proceed without unbounded delay from unrelated medium-priority work.

### 15. Deadlock and the four Coffman Conditions
A **deadlock** is a state where two or more processes/threads are each waiting for a resource held by another in the group, forming a cycle where none can ever proceed. It requires **all four** of these conditions to hold **simultaneously**:
1. **Mutual Exclusion**: at least one resource is held in a non-shareable mode.
2. **Hold and Wait**: a process holds at least one resource while waiting to acquire additional resources currently held by others.
3. **No Preemption**: resources cannot be forcibly taken away from a process — only voluntarily released.
4. **Circular Wait**: a closed chain of processes exists where each waits for a resource held by the next process in the chain.
Breaking any **one** of these four conditions is sufficient to prevent deadlock — this is the theoretical basis for every deadlock-prevention strategy in Q16.

### 16. Deadlock Prevention vs Avoidance vs Detection & Recovery
- **Deadlock Prevention**: structurally design the system so that at least one of the four Coffman conditions **can never occur** — e.g., enforce a strict global lock-acquisition ordering (eliminates circular wait), or require processes to request **all** needed resources upfront at once (eliminates hold-and-wait). Conservative and safe, but can hurt resource utilization/concurrency since it's often overly restrictive.
- **Deadlock Avoidance**: allow the conditions to potentially exist, but **dynamically analyze each resource request** before granting it, only approving requests that keep the system in a **provably "safe state"** (a state from which there's a guaranteed ordering allowing all processes to eventually complete) — the **Banker's Algorithm** (Q17) is the canonical example. Requires advance knowledge of each process's maximum resource needs.
- **Deadlock Detection & Recovery**: don't prevent or avoid deadlocks at all — let the system run freely, but **periodically check** (e.g., via a wait-for graph cycle check) whether a deadlock has actually occurred, and if so, **recover** by forcibly preempting resources or **killing/rolling back** one or more of the deadlocked processes (a "victim") to break the cycle. Simplest to implement and allows maximum concurrency in the common case, but requires ongoing detection overhead and a recovery strategy for when it does happen.

### 17. Banker's Algorithm — avoiding deadlock via Safe State analysis
The Banker's Algorithm (deadlock avoidance) works like a cautious bank manager who never lends more than they can safely cover. Each process must declare its **maximum possible resource need** upfront. Before granting any resource request, the algorithm performs a **"what-if" simulation**: it pretends to grant the request, then checks whether, from this hypothetical state, there still exists **at least one ordering** in which every currently-running process could obtain its remaining maximum needs, run to completion, and release its resources back to the pool (which then lets subsequent processes in the ordering also complete) — this is called a **Safe State**. If such a completion ordering exists, the request is **granted**; if granting the request would leave the system in a state where **no such ordering exists** (an **unsafe state** — not necessarily an immediate deadlock, but a state where deadlock *could* eventually occur), the request is **denied/deferred**, and the process must wait, even if the resources are technically currently available. This trades some resource utilization (being conservative, sometimes denying requests that wouldn't actually have caused a problem) for a mathematically guaranteed avoidance of deadlock.

### 18. Producer-Consumer (Bounded-Buffer) Problem — semaphore-based solution
Producers add items to a shared, fixed-size buffer; consumers remove items — producers must block when the buffer is full, consumers must block when it's empty, and access to the buffer itself must be mutually exclusive. The classic solution uses **three semaphores**:
- `empty` (counting semaphore, initialized to buffer capacity `N`) — tracks available empty slots.
- `full` (counting semaphore, initialized to `0`) — tracks filled slots.
- `mutex` (binary semaphore, initialized to `1`) — protects the actual buffer insert/remove operation itself.

```
Producer:
    wait(empty)        // block if buffer is full (no empty slots)
    wait(mutex)         // acquire exclusive access to buffer
        insert(item)
    signal(mutex)        // release exclusive access
    signal(full)         // one more filled slot now available

Consumer:
    wait(full)          // block if buffer is empty (nothing to consume)
    wait(mutex)
        item = remove()
    signal(mutex)
    signal(empty)        // one more empty slot now available
```
This avoids **busy-waiting** entirely — `wait()` on a semaphore with count `0` puts the calling thread to **sleep** (blocked), rather than spinning, until a corresponding `signal()` wakes it. It avoids **race conditions** because the `mutex` semaphore ensures only one thread touches the buffer's internal state at a time, while `empty`/`full` correctly enforce the blocking conditions without either producers or consumers needing to poll/check buffer state manually.

### 19. Dining Philosophers Problem — and the constraint to guarantee no deadlock
Five philosophers sit around a table, each needing **two forks** (shared with neighbors) to eat; there are only five forks total (one between each pair of adjacent philosophers). If every philosopher simultaneously picks up their **left** fork first, then waits for their **right** fork, **all five** end up holding one fork each and waiting forever for the next — a deadlock via **circular wait**, with all four Coffman conditions satisfied symmetrically.
The standard architectural fix: **break the symmetry** — have all philosophers pick up forks in a **consistent global order** (e.g., always pick up the lower-numbered fork first, then the higher-numbered one), **except one designated philosopher** who picks up in the opposite order (right-then-left instead of left-then-right). This asymmetry breaks the perfectly circular resource-acquisition pattern — with at least one philosopher trying to acquire forks in a different order, the resulting wait-for graph can no longer form a complete cycle among all five participants simultaneously, guaranteeing the deadlock (circular wait condition) can never occur. (Other valid fixes: limit at most 4 philosophers allowed to sit/try to eat at a time, or require picking up both forks atomically as a single all-or-nothing operation — all of these work by breaking one of the four Coffman conditions.)

### 20. Livelock vs Deadlock
In a **Deadlock**, involved processes are completely **stuck/blocked**, doing absolutely nothing — they're waiting indefinitely with no state change at all. In a **Livelock**, processes are **not blocked** — they remain **actively running and changing state** in response to each other, but their combined behavior never actually makes any real progress toward completion — they're essentially stuck in a loop of repeatedly reacting to each other without resolving anything. Classic analogy: two people in a narrow hallway both repeatedly stepping aside in the same direction to let the other pass, perpetually blocking each other despite both actively "trying" to resolve it — busy, but no progress. A common cause in software: two threads each detecting a potential conflict/deadlock and **both backing off and retrying at the exact same interval**, repeatedly colliding again on retry — resolved typically by adding **randomized backoff** so retries desynchronize over time.

## Category 3: Memory Management & Virtual Memory

### 21. Logical vs Physical Address Space; MMU translation
**Logical (virtual) address space** is the set of addresses a running **process** generates and sees — a self-contained, process-private view of memory starting conceptually from address 0, completely independent of where the process's data is actually located in RAM. **Physical address space** is the set of **actual hardware RAM addresses** where data really resides. The **Memory Management Unit (MMU)**, dedicated hardware sitting between the CPU and RAM, performs **real-time translation** of every logical address the CPU generates into the corresponding physical address, using the process's **page table** (loaded via a base register the OS sets on context switch) — this translation happens on essentially every single memory access, transparently to the running program, and is what allows every process to believe it has its own private, contiguous memory space while actually being scattered across (and isolated within) shared physical RAM.

### 22. Internal vs External Fragmentation; how Paging and Segmentation address them
- **Internal Fragmentation**: wasted space **within** an allocated block — occurs when memory is allocated in **fixed-size chunks** (like fixed-size pages) and a process's actual data doesn't perfectly fill the last chunk it's given, leaving unusable leftover space **inside** that allocated unit.
- **External Fragmentation**: wasted space **between** allocated blocks — occurs when free memory exists but is **scattered in small, non-contiguous fragments** throughout memory, such that no single free fragment is large enough to satisfy a new allocation request, even though the *total* free memory would be sufficient.
- **Paging** divides memory into **fixed-size pages/frames**, eliminating external fragmentation entirely (any free frame can hold any page — no need for contiguous space), but introduces **internal fragmentation** (the last page of a process is rarely exactly full).
- **Segmentation** divides memory into **variable-sized, logically meaningful segments** (e.g., code segment, stack segment, heap segment) matching a program's natural structure, which avoids internal fragmentation (segments are sized exactly to what's needed) but reintroduces **external fragmentation**, since variable-sized segments scattered and freed over time leave irregular gaps, similar to the classic dynamic-memory-allocation fragmentation problem.
Most modern systems use **paged segmentation** (segments internally divided into pages) to get the benefits of both.

### 23. Paging — Page Table structure and mapping
Paging divides a process's **logical address space into fixed-size pages**, and physical memory into equal-sized **frames**. The **Page Table** (one per process) is the mapping structure: each entry maps a **logical page number → physical frame number**, and typically also stores metadata bits per entry — a **valid/invalid bit** (is this page currently actually loaded in RAM, or does accessing it need to trigger a page fault?), a **dirty bit** (has this page been modified since loaded — relevant for deciding whether it needs to be written back to disk before eviction), and **protection bits** (read/write/execute permissions). A logical address is split into a **page number** (used as an index into the page table to find the frame number) and a **page offset** (the position within that page/frame, copied unchanged) — the MMU concatenates the looked-up frame number with the unchanged offset to produce the final physical address.

### 24. Translation Lookaside Buffer (TLB) — hit/miss impact on effective memory access time
The **TLB** is a small, extremely fast **hardware cache** (sitting inside or very close to the CPU/MMU) that stores **recently-used page-number → frame-number translations**, avoiding the need to walk the full page table (which lives in main memory) on every single memory access. On a **TLB hit**, the translation is found instantly in the TLB, and the effective memory access time is essentially just the normal RAM access time (~1 memory access). On a **TLB miss**, the MMU must fall back to walking the actual **page table in main memory** to find the translation (potentially multiple memory accesses for multi-level page tables), **then** perform the actual data access — so a miss roughly **doubles (or worse) the effective memory access time** compared to a hit. Because of this large cost gap, TLB hit rate is a critical performance factor — this is exactly why context switches (which typically flush or partially invalidate the TLB, since the new process has an entirely different address mapping) are expensive: the first several memory accesses after a switch are likely to be TLB misses until the cache "warms up" again for the new process.

### 25. Virtual Memory — running a process larger than physical RAM
**Virtual Memory** is an abstraction that gives every process the illusion of a large, contiguous, private address space, **independent of how much physical RAM is actually installed** and independent of what other processes are doing. It achieves this by keeping only the **currently-needed portions** of a process's address space actually resident in physical RAM at any given time, while the **rest resides on disk** (in a swap file/partition) — pages are brought into RAM **on demand** as they're actually accessed (demand paging), and pages not currently in active use can be **evicted back to disk** to free up frames for other pages that are needed right now. This means a process's total compiled memory footprint can vastly exceed physical RAM, as long as its **actively used working set** at any given moment fits — the OS transparently swaps portions in and out via the page-fault mechanism (Q26), giving the illusion of near-unlimited memory at the cost of disk I/O latency whenever a needed page isn't currently resident.

### 26. Page Fault — step-by-step handling sequence
A **Page Fault** is a hardware trap/interrupt raised by the MMU when a running process accesses a page that's marked **invalid** in its page table (i.e., not currently loaded in physical RAM). The kernel's page fault handler then:
1. **Traps to the kernel** — the CPU switches to kernel mode and invokes the OS's page fault handler, saving the process's current execution state.
2. **Validate the access** — the OS checks whether this was a **legitimate** access to a valid part of the process's address space that's simply not currently loaded (normal case), or an **illegal** access outside the process's valid address space (in which case it terminates the process, e.g., a segmentation fault).
3. **Find a free frame** — locate a free physical memory frame; if none is available, run a **page replacement algorithm** (Q27–28) to select a victim page to evict, writing it back to disk first if it's **dirty** (modified since loaded).
4. **Load the required page from disk** into the (now-available) physical frame — this is the actual disk I/O, the slowest step by far.
5. **Update the page table** for the faulting process, marking the page as **valid** and recording its new frame number; also update the TLB.
6. **Resume the process**, re-executing the instruction that originally caused the fault — which now succeeds, since the required page is present.

### 27. Belady's Anomaly
**Belady's Anomaly** is the counter-intuitive phenomenon where, for certain page-replacement algorithms, **increasing the number of available page frames** can actually **increase** the number of page faults, rather than decrease or keep it the same as intuitively expected. This paradox occurs specifically with the **FIFO (First-In-First-Out)** page replacement algorithm — because FIFO's eviction choice depends only on **arrival order**, not actual usage patterns, adding more frames changes *which specific pages* end up getting evicted at various points in a way that isn't monotonically "better," occasionally leading to a worse fault sequence for certain reference strings. Algorithms based on the actual **stack property** (where the set of pages held with `k` frames is always a subset of what would be held with `k+1` frames) — such as **LRU** and **Optimal** — are mathematically **immune** to Belady's Anomaly, since more frames can never cause a page held with `k` frames to be evicted with `k+1` frames.

### 28. FIFO vs Optimal (OPT) vs LRU page replacement
- **FIFO**: evicts the page that has been **in memory the longest**, regardless of how recently or frequently it's actually been used. Simple to implement (just a queue), but performs poorly in practice and suffers from Belady's Anomaly.
- **Optimal (OPT)**: evicts the page that **will not be used for the longest time in the future** — provably the theoretically best possible strategy, minimizing page faults. Impossible to implement in a real running system (it requires knowing the future reference sequence in advance), but used as a **benchmark/upper bound** to evaluate how close other algorithms come to ideal performance.
- **LRU (Least Recently Used)**: evicts the page that **hasn't been accessed for the longest time in the past**, using historical access patterns as a practical proxy/approximation for OPT's future-knowledge requirement — based on the reasonable assumption (temporal locality) that pages unused recently are also unlikely to be needed again soon. LRU performs close to OPT in most real workloads and is immune to Belady's Anomaly.
**LRU (and its many practical approximations/variants)** forms the logical backbone of modern **cache architectures** broadly — CPU caches, database buffer pools, and OS page caches all use LRU or LRU-derived eviction policies (like LRU-K, Clock/Second-Chance as an efficient LRU approximation) because true LRU tracking has overhead, but its core "recency implies future usefulness" principle is a strong, empirically validated heuristic across nearly all caching contexts.

### 29. Thrashing — cause and fix
**Thrashing** is a pathological state where the system spends the **overwhelming majority of its time servicing page faults** (swapping pages in and out of disk) rather than executing actual useful CPU instructions — overall system throughput collapses even though the CPU/disk appear extremely "busy." It's caused when the **combined working set** of all currently-running processes **exceeds available physical RAM** — each process doesn't have enough frames to hold its actively-needed pages, so as soon as one page is evicted to make room for another, it gets faulted back in almost immediately (because it was still actively needed), evicting yet another needed page in turn, in a self-defeating cascade; increasing the **degree of multiprogramming** (running more processes concurrently) beyond what physical memory can support actually **makes thrashing worse**, not better, since it further reduces each process's available frame share. **Fixes**: reduce the degree of multiprogramming (suspend/swap out some processes entirely, giving remaining processes enough frames for their actual working sets), add more physical RAM, or use a **working-set model**-based allocation strategy that ensures each process is only ever allowed to run if its estimated actual working set can be accommodated in memory.

### 30. Inverted Page Table — why used in 64-bit systems
A traditional (hierarchical/forward) page table has **one entry per virtual page** of a process's address space — with 64-bit address spaces being astronomically large, even a mostly-sparse, multi-level hierarchical page table can still consume significant memory just to represent the mapping structure, and this overhead exists **per process**. An **Inverted Page Table** flips the indexing: instead of one entry per *virtual* page (indexed by virtual page number, potentially huge), it has **exactly one entry per physical frame** (indexed by physical frame number) — since the amount of **physical RAM** is comparatively small and fixed regardless of how large the virtual address space theoretically is, the inverted page table's size scales with **physical memory size**, not virtual address space size, and there's only **one single table shared system-wide** (each entry records which process/virtual-page currently occupies that physical frame) rather than one table per process. This dramatically reduces memory overhead for page table storage in 64-bit systems, at the cost of needing an associative/hashed lookup (since you can no longer directly index by virtual page number) to find a given virtual address's frame, typically accelerated via a hash table alongside the inverted table itself.

## Category 4: Storage Systems, Kernel Architecture & System Calls

### 31. System Call — User Mode to Kernel Mode transition; 3 POSIX examples
A **System Call** is the controlled, well-defined interface through which a user-space program requests a privileged service from the OS kernel (e.g., file I/O, process creation, network access) — operations a regular user-mode program isn't permitted to perform directly, since it lacks direct hardware/privileged access. The transition from **User Mode (Ring 3)** to **Kernel Mode (Ring 0)** happens via a special **trap/software interrupt instruction** (e.g., `syscall`/`int 0x80` on x86) — the CPU switches privilege levels, saves the user context, and jumps to a fixed, kernel-defined entry point (the system call handler), which looks up the requested system call number in a table and executes the corresponding kernel routine with full hardware access. Once complete, control returns to user mode with the result. Three standard POSIX examples: **`fork()`** (create a new child process), **`exec()`** (replace the current process image with a new program), **`read()`** (read data from a file descriptor into a buffer).

### 32. What happens during `fork()`; Copy-on-Write (COW) optimization
`fork()` creates a **new child process** that is (conceptually) an exact duplicate of the calling parent process — same code, same data, same open file descriptors, same execution point (both parent and child resume execution right after the `fork()` call, distinguished only by `fork()`'s return value: `0` in the child, the child's PID in the parent). Naively, this would require the OS to **immediately copy the entire parent's address space** (heap, stack, data) into a new physical memory region for the child — expensive, and wasteful, since many `fork()` calls are immediately followed by an `exec()` that discards this copied memory anyway. **Copy-on-Write (COW)** optimizes this: instead of copying immediately, the child's page table entries are set to **point to the exact same physical frames as the parent**, marked **read-only** for both. As long as neither process modifies that shared memory, no actual copying ever happens. The moment **either** process attempts to **write** to a shared page, that write triggers a **page fault** (since the page is marked read-only) — the kernel's fault handler then makes an actual **private copy of just that one page** for the writing process, updates its page table to point to the new copy, and lets the write proceed — so copying happens **lazily, one page at a time, only for pages that actually get modified**, dramatically reducing the cost of `fork()` in the common case.

### 33. Monolithic Kernel vs Microkernel — stability, security, speed
- **Monolithic Kernel** (e.g., Linux): the **entire OS** — process management, memory management, file systems, device drivers, networking — runs together as **one large program in kernel space (Ring 0)**, with direct function calls between components. **Speed**: very fast, since inter-component communication is just direct in-kernel function calls with no context-switch/message-passing overhead. **Stability/Security**: weaker isolation — a bug or crash in **any** kernel component (e.g., a faulty device driver) can crash or compromise the **entire kernel**, since everything shares the same privileged address space.
- **Microkernel** (e.g., Minix, QNX): the kernel itself is kept **minimal** — only the most essential services (basic IPC, minimal scheduling, minimal memory management) run in privileged kernel space; everything else (file systems, device drivers, network stacks) runs as **separate user-space processes**, communicating with the kernel and each other via **message passing**. **Stability/Security**: much stronger isolation — a crashing driver or file-system bug runs in its own isolated user-space process and can be restarted independently without taking down the whole system. **Speed**: slower for operations that would be a direct function call in a monolithic kernel, since crossing process/privilege boundaries via message passing/IPC (with associated context switches) is inherently more expensive than an in-kernel function call.
The practical trade-off: monolithic kernels favor raw performance (why Linux, used in most high-performance/low-latency server contexts including banking infrastructure, is monolithic — with loadable kernel modules as a partial compromise for extensibility); microkernels favor fault isolation and security, more common in safety-critical embedded/real-time systems.

### 34. Synchronous (Blocking) I/O vs Asynchronous (Non-blocking) I/O; why async matters for HFT gateways
- **Synchronous I/O**: the calling thread **blocks/waits** until the I/O operation (disk read, network call) fully completes before it can proceed to its next instruction — the thread is idle (in a Waiting state) for the entire I/O duration, doing no other useful work.
- **Asynchronous I/O**: the calling thread **issues the I/O request and immediately continues executing other work**, without waiting — it's later notified (via a callback, event, future/promise, or polling a completion status) once the I/O operation actually finishes in the background.
For **high-frequency trading gateways**, asynchronous I/O is critical because these systems must handle **massive numbers of concurrent network connections/market-data streams** with **ultra-low latency** — if a thread blocked synchronously on every network read/write, you'd need one thread per concurrent connection (expensive, doesn't scale — ties back to Q9's thread-pool reasoning), and any single slow I/O operation would stall that thread's ability to process other, unrelated, time-critical events. Async I/O lets a small, fixed number of threads efficiently multiplex across thousands of concurrent I/O operations (via mechanisms like `epoll`/`io_uring` on Linux), maximizing CPU utilization and minimizing the latency added by I/O waits — exactly the throughput-and-latency profile a trading gateway needs under extreme concurrent load.

### 35. Device Drivers; Interrupts vs Polling
A **Device Driver** is a specialized kernel (or kernel-adjacent) software module that translates the OS's generic I/O requests into the **specific low-level commands** a particular hardware device understands, abstracting hardware-specific details away from the rest of the OS and applications — the OS talks to a generic "block device" or "network device" interface, and the driver handles the actual device-specific register-level communication.
- **Interrupts**: the hardware device itself **signals the CPU** (via a dedicated interrupt line) the moment it has data ready or has completed an operation — the CPU is otherwise free to do other work in the meantime, and only pauses to handle the device when actually notified. Efficient for devices with **infrequent, unpredictable** events (keyboard input, network packet arrival).
- **Polling**: the CPU **repeatedly checks (in a loop)** the device's status register to see if it's ready, rather than waiting to be notified. Simple, but wastes CPU cycles checking a device that isn't ready yet, and can also introduce latency if the polling interval isn't tight enough — though for devices with **extremely high-frequency, near-continuous** data (like a very fast network card under heavy load), polling can actually **outperform** interrupts by avoiding the per-interrupt context-switch/handler overhead multiplied across an enormous event rate (this is exactly why Linux's `NAPI` and technologies like `io_uring`/kernel-bypass networking blend polling and interrupts adaptively for high-throughput scenarios like trading infrastructure).

### 36. Direct Memory Access (DMA)
**DMA** is a hardware mechanism that allows peripheral devices (disk controllers, network cards) to **transfer data directly to/from main memory**, **without requiring the CPU to manage the transfer byte-by-byte**. Without DMA, the CPU itself would have to execute a loop reading each individual byte/word from the device and writing it to memory (called **Programmed I/O**) — fully occupying the CPU for the entire transfer duration, which is enormously wasteful for large data transfers. With DMA: the CPU simply **initiates** the transfer by telling the **DMA controller** the source, destination, and size of the transfer, then the CPU is **completely free** to continue executing other instructions while the DMA controller independently manages the actual data movement over the system bus; once the transfer completes, the DMA controller raises an **interrupt** to notify the CPU. This offloads the tedious, high-volume data-movement work entirely off the CPU, letting it spend its cycles on actual computation rather than acting as a data-shuttling middleman — essential for high-throughput systems moving large volumes of market data or transaction logs between disk/network and memory.

### 37. Journaling File System — preventing corruption across crashes/power failures
A **Journaling File System** maintains a separate, sequential **journal (log)** area on disk where it records the **intent** of upcoming file system metadata changes (and sometimes data changes) **before** actually applying those changes to the main file system structures — directly analogous to a database's Write-Ahead Log (from your DBMS prep). When a metadata operation is about to occur (e.g., creating a file, which involves updating multiple on-disk structures: inode table, directory entry, free-space bitmap), the file system first writes a **journal entry describing the full intended change**, marks it committed once fully written, and only **then** applies the actual changes to the real file system structures. If the system **crashes or loses power mid-operation** (potentially leaving the actual file system structures in an inconsistent, half-updated state), on reboot the file system **replays the journal**: any journal entry that was fully committed but whose corresponding real changes weren't confirmed complete gets **re-applied (redone)**; incomplete/uncommitted journal entries are simply **discarded**. This avoids the need for a full, extremely slow file-system-wide consistency scan (like old `fsck` on non-journaling filesystems) after every crash, and guarantees the file system metadata always returns to a **consistent** state, even though the very last in-progress operation before the crash might be lost, rather than the whole file system becoming structurally corrupted.

### 38. Hard Links vs Soft Links (Symbolic Links) — inode references
Every file on a Unix-like file system is represented by an **inode**, which stores the file's actual metadata and a pointer to its data blocks; a **directory entry** (filename) is just a mapping from a name to an inode number — a file's "name" isn't stored in the inode itself.
- **Hard Link**: a **second directory entry pointing to the exact same inode number** as the original file — there's no meaningful distinction between "the original" and "the hard link" after creation; both are equally valid names for the same underlying data. The inode's **link count** is incremented; the actual file data/inode is only deleted once the link count drops to **zero** (i.e., every hard link referencing it has been removed). Hard links **cannot** span across different file systems/partitions (since inode numbers are only unique within a single file system) and **cannot** reference directories (to prevent filesystem-structure cycles).
- **Soft Link (Symbolic Link)**: a **separate, special file** that contains, as its "data," the **path (text string)** to the target file — it has its **own distinct inode**, and merely stores a pointer-by-path, not a direct inode reference. If the original target file is deleted or moved, the symlink becomes a **"dangling"/broken link** (it still exists, but resolving it fails), since it never had a direct inode-level relationship — just a path string that may no longer be valid. Soft links **can** span across file systems and **can** point to directories.

### 39. Spooling and Buffering — managing CPU/peripheral speed disparities
- **Buffering**: temporarily holds data **in memory** while it's being transferred between two entities operating at **different speeds** (e.g., a fast CPU producing data and a slow disk consuming it, or vice versa) — smoothing out the speed mismatch so the faster component doesn't have to constantly stall waiting for the slower one on every single unit of data; data is accumulated/released in efficient chunks rather than one item at a time.
- **Spooling (Simultaneous Peripheral Operations On-Line)**: specifically manages access to a device that **can only serve one job/request at a time** (classically a printer) by having multiple processes write their output to a **disk-based queue (spool)** rather than directly and exclusively to the device — the device then processes queued jobs one at a time from the spool, independently of when the originating processes actually ran. This lets multiple processes "use" a single slow, exclusive-access device seemingly concurrently, without having to block waiting for direct, serialized device access themselves — they just write to the fast spool and move on.
Both exist to decouple a fast producer/consumer from a slower, differently-paced counterpart, but buffering is about smoothing raw speed mismatches for a data stream, while spooling specifically solves the problem of multiple independent clients needing serialized access to one exclusive-use device.

### 40. SCAN (Elevator) and C-SCAN disk scheduling
Both algorithms aim to minimize total disk **seek time overhead** by servicing pending read/write requests in an order that minimizes the physical movement of the disk's read/write head across the platter, rather than servicing requests in arrival order (which can cause the head to swing back and forth wastefully — as FCFS disk scheduling would).
- **SCAN (Elevator Algorithm)**: the disk head moves in **one direction** (e.g., toward higher cylinder numbers), servicing every pending request it passes along the way, until it reaches the **end of the disk** — then it **reverses direction** and sweeps back the other way, again servicing requests it passes — exactly like an elevator serving floor requests in one direction before reversing. This gives reasonably fair, low-total-seek-distance servicing, but requests just missed at the "far end" right after the head reverses direction can experience longer relative wait times than requests near the middle.
- **C-SCAN (Circular SCAN)**: also sweeps in one direction servicing requests, but upon reaching the end of the disk, it does **not** service requests on the way back — instead it **immediately jumps back to the beginning** of the disk (without servicing anything during that return jump) and then starts a **new sweep in the same original direction** again. This treats the disk cylinders as a **circular list**, providing **more uniform/predictable wait times** across all cylinder positions compared to SCAN, since every request is always serviced during exactly one consistent-direction sweep rather than potentially getting serviced on either an outbound or a return sweep depending on timing — at the cost of the "wasted," non-servicing return jump.
